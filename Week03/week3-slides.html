Today's finish line

Build a state machine

Your deliverable

A machine that tracks what the robot is doing, a passing test for every transition, and it driven by controller buttons in the sim.

The machine

Three states, a few rules

        intake (A)          score (B)
  IDLE ───────► INTAKING ───────► SCORING
   ▲                                 │
   │       score (B) — done          │
   └─────────────────────────────────┘
  STOP (Y) from ANY state ──► IDLE
Idea 1 — enum

Name the states

public enum RobotState { IDLE, INTAKING, SCORING; }

Not 0/1/2 — real names. You literally can't use a state that doesn't exist.

Idea 2 — switch

Branch per state

switch (state) {
  case IDLE:     if (intake) state = RobotState.INTAKING; break;
  case INTAKING: if (score)  state = RobotState.SCORING;  break;
  case SCORING:  if (score)  state = RobotState.IDLE;     break;
}

Two traps: == compares, = assigns · every case needs break.

Idea 3 — lambdas

A button is a supplier

superstructure.update(driver::getAButton, ...);

driver::getAButton is a BooleanSupplier — a true/false the machine asks for each loop. This is exactly how Week 4's button bindings work.

Why we still test

A failing test points at the bug

@Test void fullIntakeScoreCycle() {
  assertEquals(RobotState.INTAKING, s.update(true,false,false));
  assertEquals(RobotState.SCORING,  s.update(false,true,false));
}

Break one transition and the test names it. Run: ./gradlew test.
